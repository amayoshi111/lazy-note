# php2shell と node2shell の1か月と、攻撃側が伸びていくことへの疲れ

## 投稿日時

- 2026/11/23 22:59

## 筆者名

- amkkr

## 本文

10月21日、同じ日に PHP と Node.js の両方に致命的な脆弱性の修正が出た。通称 php2shell と node2shell。どちらも CVSS v4.0 で 9.2、認証なしのリモートコード実行につながりうる。調べたことと、読んでいて感じたことを分けて書いておく。

### php2shell

[PHP2Shell](https://en.wikipedia.org/wiki/PHP2Shell) は CVE-2026-109618 と CVE-2026-109619 の2件の総称で、名付けたのは Wiz だ。[Sansec の解説](https://sansec.io/research/php2shell)によると、どちらも use-after-free で、リクエスト中に `memory_limit` を超えるなどして致命的エラーが起きると、ネイティブコードが後始末をしないまま中断され、あとのリクエストや再利用されたワーカーが解放済みのメモリを生きたデータとして扱ってしまう。該当コードは 2012 年の PHP 5.4.0 から存在していたという。修正版は 8.5.12 / 8.4.27 / 8.3.36 / 8.2.35。7.4・8.0・8.1 はソースのパッチのみで、公式バイナリは出ていない。

時系列も押さえておく。Sansec の表では、8月1日に Calif が複数の RCE 経路を見つけ、8月11日に PHP へ報告、8月24日に Wiz も報告している。10月20日に詳細が流出し、21日に修正版がリリースされた。そして Amazon の観測では、10月17日、つまり修正版リリースの4日前にすでに攻撃の試行があった。

AI の関与は、[php2shell.com](https://www.php2shell.com/) に自己申告で書かれている。Wiz は発見・エクスプロイト開発・パッチ検証に Gemini と GPT 系のモデルを使ったとしていて、Calif の研究者も OpenAI のモデルを使って見つけたと Wikipedia にある。

一方で、実際にどれだけ撃たれるかには見解の割れがある。Sansec は、公開 PoC を試した研究者の話として、デフォルトの PHP 構成では動かず、多くはアプリ側にローカルファイルインクルードのバグが要ると書き、大規模な攻撃は当初の予想より起きにくいとしている。[CrowdStrike](https://www.crowdstrike.com/en-us/blog/crowdstrike-protects-customers-from-php-rce-zero-days/) は自社の検証で、匿名の POST 1発から mod_php のワーカーにコマンドを実行させるところまで確認したとしている。ただしその検証は `memory_limit` を下げた環境で行われ、既定値のままでは届かないという趣旨の記述もあるようだ。つまり両者は正面から食い違っているというより、前提とする設定が違うのかもしれない。実際の危険度がどちらに近いのか、自分には判断材料が足りない。

### node2shell

[Node2Shell](https://www.sophos.com/en-us/blog/node2shell-cve-2026-111497-in-active-exploitation) は CVE-2026-111497。Node.js が同梱する Brotli デコーダの範囲外書き込みで、修正版は 22.23.4 / 24.22.1 / 26.12.1。[Akamai の解説](https://www.akamai.com/blog/security-research/inside-node2shell-closer-look-cve-2026-111497)によれば、ブロック切り替えが不正なデータを「形式エラー」ではなく「入力がまだ足りない」と扱ってしまい、8バイトの内部バッファの末尾を越えて書き込み続ける。

厄介なのは到達経路だ。[Semgrep](https://semgrep.dev/blog/2026/patch-your-node-and-eat-your-brotli-or-you-wont-get-dessert/) が書いているとおり、Express 5 の body-parser 2.x は inflate が既定で有効なので、`Content-Encoding: br` のリクエストボディが JSON として解釈される前にデコーダへ渡る。自分で Brotli を触っていなくても、フレームワークの既定動作で踏む。[Aikido](https://www.aikido.dev/blog/python-packages-vulnerable-node2shell-brotli-cve-2026-111497) によると、Python の Brotli、.NET、Java にも波及している。

もうひとつ気になったのは経緯だ。Aikido の記述では、根本原因のコードは Brotli の上流で2月27日にすでに直っていたのに、セキュリティ問題として認識されず、リリースに載ったのは10月21日の 1.2.1 だった。報告したのは OpenAI の Codex Security チームとある。AI がどう使われたかまでは、自分が読んだページには書かれていなかった。悪用についても、10月22日時点では Node.js への実攻撃は未確認という報道があり、27日に CISA が KEV に追加している。

### 攻撃側が伸びている、という疲れ

ここからは体感の話だ。

読んでいて疲れたのは、個々の脆弱性の深刻さよりも、**防ぐ側が毎回ゼロから追いかける構図が、AI で薄まるどころか濃くなっている**感覚のほうだった。

ただ、「攻撃側が圧倒的に伸びている」と言い切れるほどの材料は、自分は持っていないと思う。今回の2件で AI の関与がうかがえるのは、Wiz、Calif、OpenAI といった**防御側・研究側**だ。php2shell は少なくとも、AI の支援を受けた研究者が見つけ、報告を経て修正された。攻撃側の AI 利用を示す材料は、自分が読んだ範囲には出てこなかった。実害の見積もりも割れている。「攻撃が圧倒的」は、この範囲では事実として確認できていない。

事実として見えているのは別のことだ。**発見から修正まで、そして修正から悪用までの猶予が短い**。php2shell は公開より前に試行があった。node2shell は半年以上前に上流で直っていたバグが、セキュリティ問題として認識されないまま修正版に載らず残っていた。Semgrep も、AI ツールで研究者も攻撃者も何年分ものパッチを解析できるようになった、という趣旨のことを書いている。直った事実が、そのまま攻撃者への地図になりうる。

つまり自分が疲れている正体は、攻撃側の能力が伸びたことそのものより、**非対称性の強まり**だと思う。攻撃側は1つ通せば勝てて、防御側は全部を塞ぎ続けないといけない。AI は両方の速度を上げるが、塞ぐ側は「全部」の長さがそのまま負荷として残る。防御もやりやすくなったとは思うが、その分だけ楽になった実感はあまりない。

### 深夜対応をやると決めたとき

それでも、今回は深夜に対応すると決めた。

決めた瞬間はちょっと気分がよかった。誰かに頼まれたわけでも、見ている人がいるわけでもないのに、「今夜これを塞ぐのは自分だ」と決めたときに、少しだけヒーローになれた気がした。

冷静に見ると、これは疲れと表裏の感情だとも思う。構図が非対称だから、塞ぐ側にはどうしても「自分がやらなければ誰もやらない」場面が出てくる。そこで腹をくくることに、少し高揚する。ただ、その高揚で深夜の作業の負担が減るわけではない。ヒーロー気分は、翌朝の自分の睡眠を前借りしているだけかもしれない。

ただ、あの感覚をなかったことにはしたくない。疲れていることと、塞ぐと決めたときに悪くない気分になることは、両方本当だ。当面はこの二つを抱えたまま、パッチを当て続けることになりそうだ。
